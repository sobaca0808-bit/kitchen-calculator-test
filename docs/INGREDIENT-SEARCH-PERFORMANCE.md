# Оптимизация поиска ингредиентов — 21 ноября 2026

Основа: PR №42, `c24d201f6889a2362be09f138ae683e35b4e3626`.
Ветка: `perf/ingredient-search`; целевая ветка PR —
`feature/unified-establishment-expenses`, чтобы не включать повторно весь PR №42.
Публикация, слияние и изменение `main` не выполняются.

## Изменение

В `js/app.js`, `setupSearch.draw`, сначала отбираются совпадения по названию
и альтернативным названиям. Проверка циклов вызывается только для подходящих
полуфабрикатов. Для продуктов она не нужна: у них нет ссылок на рецептуры.
Снимок всей базы для этой проверки создаётся только при наличии подходящего
полуфабриката. Продукты по-прежнему идут первыми, исходный порядок сохраняется.

Расчётные модули, CSS, шаблоны, формат JSON, хранение, фотографии, черновики и PWA
не менялись. Существующая защита файлов в `check-unified-expenses-core.py`
дополнена точным SHA-256 нового поискового блока: все остальные байты `app.js`
по-прежнему сравниваются с защищённой версией. Это не исключение для всего файла.

## Методика

- Chromium 154.0.8037.57, headless, изолированный локальный сервер.
- Искусственные базы: 100/500/2000 рецептов, половина — полуфабрикаты;
  50/250/1000 продуктов; по 10 ингредиентов в рецепте, общая вложенная заготовка.
- Профили: ширина 1440, обычный CPU; ширина 390, CPU замедлен в 4 раза.
  Второй профиль — эмуляция, а не физический Android.
- Для каждого запроса один прогрев и пять измерений; таблица показывает медианы.
- Время: обработка события ввода и два `requestAnimationFrame`. Обычный
  400-мс debounce черновика завершается между измерениями. Это не LCP и не
  оценка первого открытия приложения.
- До и после выполняется один и тот же `--benchmark` из новой ветки против двух
  отдельно собранных runtime. Измерения последовательные, другие тесты в это
  время не запускались. Все профили браузера одноразовые, данные пользователя
  и внешние публикации не используются.

## Результаты

Миллисекунды, **до → после**:

| Рецептов | CPU / ширина | Нет совпадений | Один продукт | Один полуфабрикат |
|---:|---|---:|---:|---:|
| 100 | ×1 / 1440 | 19,6 → 13,9 | 15,2 → 15,3 | 15,1 → 15,0 |
| 500 | ×1 / 1440 | 38,2 → 26,7 | 36,6 → 31,9 | 41,5 → 30,2 |
| 2000 | ×1 / 1440 | 360,9 → 122,3 | 349,6 → 138,2 | 353,3 → 148,0 |
| 100 | ×4 / 390 | 93,3 → 73,2 | 76,5 → 84,8 | 78,7 → 77,9 |
| 500 | ×4 / 390 | 196,5 → 126,9 | 193,4 → 123,7 | 171,2 → 145,2 |
| 2000 | ×4 / 390 | 1538,5 → 637,5 | 1784,2 → 690,1 | 1842,9 → 888,0 |

На 2000 рецептах поиск одного продукта ускорился в 2,53 раза на обычном профиле
и в 2,59 раза при CPU ×4. На маленькой базе стабильного ускорения всех запросов
нет: один из вариантов стал медленнее на 8,3 мс. Это узкая оптимизация больших
библиотек, а не обещание ускорить любой экран и любое устройство.

Во всех пяти повторениях число проверок циклов было:

| Запрос | До | После |
|---|---:|---:|
| Нет совпадений | 100 / 500 / 2000 | 0 |
| Один продукт | 100 / 500 / 2000 | 0 |
| Один полуфабрикат | 100 / 500 / 2000 | 1 |

Количество найденных вариантов совпало до и после во всех измерениях.

## Воспроизведение

Нужны Python 3, Node.js, доступный Playwright и Chromium. Если они находятся вне
проекта, задайте `NODE_PATH` и `CHROMIUM_PATH`; зависимости приложения менять
не требуется. Для существующего A4-набора также нужен `pdftotext`.

Соберите исходный runtime из отдельного worktree на `c24d201`, исправленный —
из этой ветки, в разные временные каталоги:

```sh
python3 scripts/build-sintez-release-candidate.py --target expenses --output /tmp/search-after
INGREDIENT_SEARCH_RUNTIME_ROOT=/tmp/search-after node tests/ingredient-search.browser.test.js
INGREDIENT_SEARCH_RUNTIME_ROOT=/tmp/search-after INGREDIENT_SEARCH_REPORT=/tmp/search-after.json node tests/ingredient-search.browser.test.js --benchmark
```

Тот же файл `tests/ingredient-search.browser.test.js --benchmark` из новой ветки
запустите с `INGREDIENT_SEARCH_RUNTIME_ROOT`, указывающим на исходный runtime.
JSON-отчёт содержит все пять замеров, количество совпадений и проверок циклов.

## Ограничения

Пустой запрос или запрос, совпадающий с большим числом полуфабрикатов, всё ещё
проверяет каждого подходящего кандидата. Общий графовый индекс, виртуализация
списков и сокращение повторных расчётов итогов в эту задачу не входят.
Числа выше не характеризуют опубликованный GitHub Pages и скорость настоящего
Android. Новая тестовая публикация не создавалась.
