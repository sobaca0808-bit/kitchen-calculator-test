# Расходы заведения

## Что обнаружено в PR №22

В исходнике `1a68adf` не было ни модели расходов, ни скрытой вкладки или готового
расчёта аренды, коммунальных платежей и зарплат. `profitability.js` считал только
продуктовую себестоимость. Упаковка уже отдельно включалась в общую калькуляцию.
Поэтому добавлен новый модуль; прежние формулы продуктов, полуфабрикатов, упаковки
и продуктовой маржи не переписывались.

Владелец выбрал правило: **месячные расходы ÷ плановые продаваемые порции всех блюд**.
Это единый активный план на месяц, средняя оценка для каждой порции. История месяцев
и распределение по времени приготовления, категориям блюд или выручке сюда не входят.

## Как пользоваться

1. Откройте заметную вкладку **«Расходы заведения»** в основной навигации.
2. Укажите месяц, общий план продаж в порциях и суммы аренды, коммунальных платежей,
   зарплат и прочих расходов. Если по статье расходов нет, введите **0**.
   Пустое поле означает, что данных ещё нет.
3. Доля на порцию пересчитывается при вводе. Нажмите **«Сохранить расходы»**,
   чтобы применить план ко всем блюдам. Не нужно вручную править каждую карточку.
4. В сохранённой калькуляционной карте включите **«Учитывать расходы заведения»**.
   Детализация и новые итоги появятся сразу под прежним блоком продуктовой маржи.
5. Меняйте число порций для просмотра/печати. Доля на одну порцию остаётся прежней,
   общая сумма расходов масштабируется. Исходный рецепт не перезаписывается.

Переключатель по умолчанию выключен и не меняет рецепт. В карте повара финансового
блока и переключателя нет. Печать калькуляционной карты соответствует выбранному
состоянию переключателя; кнопки не печатаются. Прежние варианты фото сохраняются.

## Формулы и защита от двойного учёта

Для каждой статьи: месячная сумма / план продаж. Расчётная себестоимость порции =
продуктовая себестоимость порции + упаковка на порцию + сумма долей расходов.
Результат на порцию = цена продажи − расчётная себестоимость. Маржа с расходами =
результат / цена продажи × 100%. Это результат после **указанных** затрат, не чистая прибыль.

Пример: 120 000 ₽ / 3 000 порций = 40 ₽ расходов на порцию. Продукты 30 ₽ + упаковка
5 ₽ + расходы 40 ₽ = **75 ₽**. При цене 150 ₽ новый результат — 75 ₽, маржа — **50%**.
Прежняя продуктовая маржа остаётся **80%**, фудкост — **20%**.

Накладные расходы добавляются один раз на готовое блюдо, а не на каждую вложенную
заготовку. Для упаковки используется существующий механизм, включая защиту от
совпадений с ингредиентами. Общий старый итог не используется как «продуктовая»
база для ещё одного прибавления упаковки. Закупочные продукты и упаковку не нужно
дублировать в месячных статьях. Если затрата уже включена в ингредиенты вручную,
не включайте её повторно в месячные расходы.

Расчёты выполняются заново из исходных величин; округление применяется только
к отображению. Пустой план, неизвестные статьи/закупочные цены и ошибки ввода
не подменяются нулём. При нулевой цене продажи себестоимость и отрицательный
результат известны, процент маржи не вычисляется.

## Данные и совместимость

Добавлено одно необязательное поле базы, формат JSON остаётся **version 1**:

```json
{
  "establishmentExpenses": {
    "method": "planned-portions",
    "period": "2026-11",
    "plannedPortions": 3000,
    "rent": 60000,
    "utilities": 15000,
    "payroll": 45000,
    "other": 0
  }
}
```

Поля блюд, ингредиентов, папок и фото не меняются. Производные расходы не записываются
в закупочные цены или рецепты. Старые JSON без нового поля открываются как раньше,
без автоматического добавления расходов. Неизвестные будущие поля сохраняются.

Экспорт переносит план вместе с сохранёнными карточками и фото. Существующий алгоритм
объединения JSON не изменён: новый план обрабатывается как общее поле базы. При
различии пользователь явно выбирает текущую версию или весь набор из файла; месяцы
не складываются друг с другом. Старый файл при **объединении** не удаляет местные
расходы. При явно выбранной **замене всей базы** отсутствующий план удаляется вместе
с другими отсутствующими полями — после подтверждения и резервной копии.

Используется прежнее проверенное сохранение: сравнение исходной записи, подтверждение
чтением, защита от старой вкладки и квоты. При ошибке поля остаются доступны; аварийный
JSON может сохранить введённый план. Несохранённая форма расходов предупреждает при
переходе/закрытии. Авточерновики блюд и полуфабрикатов продолжают работать отдельно.

## Изолированная проверка

Для этой доработки готовится отдельный адрес `/expenses/` с пятью собственными именами
хранилищ. Привычные `/preview/`, `/pr-22/`, main и рабочий репозиторий не меняются.
Настоящие данные не копируются, начальная база пустая. При желании переноса тестовых
рецептов используйте явный экспорт/импорт своего JSON, проверьте просмотр изменений.

Состояние публикации, фактический адрес, снимки и итоговые логи фиксируются в
[отчёте отдельного стенда](https://github.com/sobaca0808-bit/kitchen-calculator-test/blob/preview/browser/preview-hosting/expenses/PUBLICATION.md).
Этот документ описывает функциональность и сам по себе не подтверждает публикацию.

Прежде чем обновлять main или прежнюю ссылку, нужна ручная приёмка владельца.
Физический Android и настоящий принтер не проверены; автоматические проверки
используют Chrome/Chromium с мобильной шириной и касаниями и PDF A4.
